## UI behavior

The checkout page will remain deliberately small:

1. Fetch `GET /api/products`.
2. Display the three returned products with their names, server-provided display prices, and quantity controls.
3. Treat products with positive quantities as the cart.
4. Prevent submission when the cart is empty.
5. Submit only `userId`, `productId`, and `quantity`; use the required `"guest"` placeholder.
6. Display the returned `total` after success.
7. Display the API’s human-readable `error` after an HTTP 400 response.
8. Display a human-readable client message if catalogue loading or the request itself fails.

The client may display catalogue prices, but those values will never be accepted as pricing inputs by the checkout route.

## Request flow

```text
/checkout
    │
    ├── GET /api/products
    │       └── server-side fixed catalogue → HTTP 200 JSON
    │
    └── user submits non-empty cart
            │
            └── POST /api/checkout
                    ├── parse JSON; parsing failure → HTTP 400
                    ├── validate userId and items
                    ├── validate each productId and quantity
                    ├── look up every price in server catalogue
                    ├── sum unitPrice × quantity into subtotal
                    ├── call calculateDiscount(subtotal)
                    ├── total = subtotal - discount
                    └── HTTP 200 {"total": number}
                              │
                              └── checkout page renders total
```

Every validation failure will terminate with HTTP 400 and a JSON object containing only a human-readable `error` string. Validation will cover:

- Body that cannot be parsed as JSON.
- A non-object body.
- Missing, non-string, empty, or whitespace-only `userId`.
- Missing, non-array, or empty `items`.
- Non-object cart entries.
- Missing, non-string, or unknown `productId`.
- Missing, non-number, non-integer, zero, negative, or fractional `quantity`.

Additional fields will not participate in validation or calculation. In particular, a client-supplied `price`, `unitPrice`, `subtotal`, `discount`, or `total` will be ignored.

## Assumptions

- The checkout UI will not collect a user ID and will always send `"guest"`, as explicitly permitted.
- Quantity controls may represent zero as “not in cart,” but submitted items will always have quantities of at least one.
- Duplicate product IDs are not prohibited. If submitted directly to the API, each entry will contribute independently to the subtotal.
- Catalogue order will match the order given in the requirements.
- API error wording may vary by validation failure, provided every message is human-readable and uses the required JSON shape.
- No rounding will occur in the server calculation. UI formatting, if applied, will be presentational only and will not change the returned numeric value.
- The home-page heading text, link label, application title, and visual accent color are implementation choices because exact copy and color are not specified.

## Risks

- JavaScript floating-point arithmetic can expose values such as `0.1 + 0.2`; the requirements explicitly prohibit introducing rounding rules or a decimal representation.
- A future formatter or automated import tool could modify `src/lib/pricing.ts`, violating its protected status. That file must be excluded from unapproved cleanup and verified exactly before acceptance.
- If the catalogue module is ever imported into a client component, its values could enter the browser bundle. The planned dependency direction keeps it imported only by server route handlers.
- Next.js, React, TypeScript, and Vitest versions must be mutually compatible. The requirements do not provide versions, so the lockfile becomes important for reproducibility.
